# Land Scout Kazakhstan

## Быстрый вход для администратора и разработчика

Актуальная документация проекта разнесена по отдельным файлам:

- `docs/PROJECT_HANDOVER.md` - общий handover: что делает проект, какие сценарии есть, что уже реализовано и какие ограничения важно помнить.
- `docs/MASTER_SPEC_STATUS.md` - общее ТЗ со статусами задач: выполнено, частично, не сделано, отложено.
- `docs/AUCTIONS_V2_STATUS.md` - простой статус по `Аукционы v2`: что уже сделано, что частично и что осталось до полноценной единой платформы перед покупкой.
- `docs/ARCHITECTURE.md` - архитектура, модули, таблицы, задачи Celery, ключевые потоки данных.
- `docs/INTEGRATIONS.md` - Telegram, ApiPay/Kaspi, SMSC, ЕГКН, OSM, генпланы/ПДП, E-Qazyna, внутренний API и сайт `zhertap.kz`.
- `docs/WEB_CABINET_ARCHITECTURE.md` - публичный сайт, веб-регистрация, личный кабинет, Telegram linking, trial и feedback.
- `docs/OPERATIONS.md` - эксплуатация, деплой, backup, диагностика и типовые проблемы.
- `docs/CODEX_START.md` - короткий стартовый контекст для нового чата Codex.

Если вы открыли проект в новом чате Codex, начните с `docs/CODEX_START.md`.

Публичный сайт `https://zhertap.kz`, личный веб-кабинет, Telegram-бот и операторская панель для автоматического предварительного поиска мест под ЛПХ
и садоводство в Казахстане. Поиск работает программно с публичными данными ЕГКН и OSM, а также с
загруженными оператором официальными геопривязанными слоями генплана/ПДП. Учетная запись
Codex для обработки заявки не нужна.

При `/start` бот сначала показывает стоимость, состав услуги и ограничения результата.
Справочники открываются только после явного согласия пользователя. Версия правил и время
нажатия сохраняются в заявке.

Перед правилами пользователь выбирает `Қазақша` или `Русский`. Выбранный язык сохраняется в
заявке и применяется ко всему клиентскому сценарию: правилам, справочникам ЕГКН, подтверждению
параметров, статусам, сообщениям об ошибках и отсутствии результатов, оплате и полному отчету.
Русские названия используются внутри запроса к ЕГКН, а клиенту показываются локализованные
названия из казахского или русского справочника.

Сервис прямо обозначается как независимый частный информационный сервис. Для доказуемости
согласия в заявке сохраняются версия, время и точный текст условий, показанный клиенту.
Команды `/offer` и `/privacy` повторно показывают условия услуги и обработку данных.

Перед приемом оплаты заполните реальные сведения исполнителя в `.env`:

```dotenv
SERVICE_PROVIDER_NAME=Полное ФИО или наименование ИП
SERVICE_PROVIDER_STATUS=ИП или иной действительный статус
SERVICE_PROVIDER_ID=ИИН/БИН, если должен сообщаться клиенту
SERVICE_PROVIDER_ADDRESS=Адрес для обращений
SERVICE_PROVIDER_CONTACT=Телефон, e-mail или Telegram для обращений
DATA_STORAGE_LOCATION=Республика Казахстан
DATA_RETENTION_MONTHS=12
PAYMENT_URL=https://pay.kaspi.kz/pay/l31wvjsj
```

Production работает на `<production-host>` (`<production-hostname>`) и домене `https://zhertap.kz`. Старые/private `172.*` адреса не использовать как цель боевого деплоя.

Боевые релизы публикуются через отдельную ветку `production`. Сервер проверяет
её по HTTPS и запускает `tools/deploy_production.sh`: делает резервную копию
PostgreSQL, принимает только fast-forward, применяет Alembic-миграции,
пересобирает контейнеры приложения и проверяет `/health`. Ветку `production`
нельзя обновлять через force-push.

Эти поля используются в правилах, оферте и политике обработки данных. Значения должны
соответствовать фактическим регистрационным, налоговым и платежным сведениям исполнителя.
`PAYMENT_URL` открывается по кнопке оплаты через Kaspi.

## Как проверяется место

1. Пользователь выбирает профиль, область, район и населенный пункт из справочников:
   `ЛПХ · 10 соток`, `ЛПХ(новый поиск)` или `Садоводство · 12 соток`. Новый поиск ЛПХ
   дополнительно спрашивает вид надела и расчетный водный профиль: 15 соток (`0.15 га`)
   для орошаемой либо 25 соток (`0.25 га`) для неорошаемой земли.
   Если у городского района нет отдельного списка населенных пунктов (например, районы
   Шымкента), система автоматически использует официальный районный контур WFS ЕГКН.
   Большой контур обрабатывается частями, чтобы не превышать лимит объектов одного ответа.
2. Worker находит административные границы через REST-каталог ЕГКН.
3. Загружает зарегистрированные участки слоя `egkn:u_view` через WFS.
4. Объединяет геометрию всех участков и вычитает ее из территории поиска.
5. В оставшихся промежутках строит квадрат выбранного профиля: 1 000 м² для прежнего ЛПХ,
   1 200 м² для садоводства либо 1 500/2 500 м² для нового ЛПХ.
6. Кандидат принимается только когда весь квадрат лежит в промежутке и не пересекает
   зарегистрированные участки публичного слоя ЕГКН.
7. Ближайший зарегистрированный участок ищется с тем же назначением: ЛПХ для профиля ЛПХ,
   садоводство для профиля садоводства. Его кадастровый номер служит только ориентиром.
8. OSM проверяется по геометрии: варианты, пересекающиеся с нанесенными дорогами, зданиями,
   водой, кладбищами, свалками, карьерами, охраняемыми территориями и инфраструктурными
   объектами, исключаются.
9. Расчетный квадрат должен находиться не дальше 15 м от границы существующего участка с
   выбранным назначением; удаленные точки в полях и дорожных коридорах не выдаются.
   Прямое пересечение с кладбищем исключает вариант, а близость без пересечения снижает рейтинг.
10. Квадрат должен целиком находиться в активном разрешающем слое официального генплана/ПДП
    и не пересекать загруженные запретные зоны или красные линии с защитным буфером.

`URBAN_PLAN_CHECK_MODE=strict` заставляет систему сначала искать официальный слой. Если для
территории не загружен геопривязанный разрешающий слой, бот сначала не отправляет координаты,
не расходует бесплатный лимит и не предлагает оплату. Вместо этого клиент получает подробное
предупреждение и кнопку `Получить предварительно без генплана`. После нажатия сохраняются
Telegram user ID, время и полный текст отдельного согласия, затем продолжается обычная
бесплатная или платная выдача. Такой отчет заметно помечается как не проверенный по генплану,
ПДП, функциональным зонам и красным линиям.

Если официальный слой существует, но кандидат находится вне разрешенной территории или
пересекает красную линию/запретную зону, кнопка обхода не показывается. Наличие PDF или
картинки генплана без достоверной геопривязки не считается автоматической проверкой.

Ссылка на документ принимается только с доменов из `URBAN_PLAN_SOURCE_DOMAINS`. Исходное
имя GeoJSON, его SHA-256 и администратор, выполнивший загрузку, сохраняются для аудита.

Пустое место на публичном слое ЕГКН не доказывает государственную собственность, юридическую
свободу земли или отсутствие фактических объектов на местности. Эти сведения подтверждаются
акиматом, землеустроителем и выездным осмотром.

По статье 102 Земельного кодекса ЛПХ состоит из приусадебного и полевого наделов.
Приусадебный надел находится в границах сельского населенного пункта и допускает жилой дом
при соблюдении градостроительных требований; полевой предназначен только для производства
сельхозпродукции. Понятия орошаемой и неорошаемой земли влияют на предусмотренный законом
размер бесплатного предоставления ЛПХ, но публичный слой не позволяет надежно установить
этот правовой статус для незарегистрированного промежутка.

В режиме `ЛПХ(новый поиск)` выбранные пользователем признаки используются как параметры
геометрического расчета и текста отчета, а не как сведения ЕГКН о пустой земле. Орошаемый
профиль повышает вес близости нанесенного в OSM источника воды, но близость воды не доказывает
наличие оросительной сети, гарантированного водоснабжения или права водопользования. Полевой
профиль не получает баллы за электричество и септик и содержит запрет трактовать результат
как место для жилого дома. Поиск остается внутри контура выбранной административно-
территориальной единицы ЕГКН и требует подтверждения проекта земельно-хозяйственного
устройства или территории административного подчинения.

Норма 0,15/0,25 га относится ко всему ЛПХ, включая приусадебный и полевой наделы, а не к
каждому наделу отдельно. Бот не распределяет площадь между ними и не утверждает, что найденное
место официально является выбранным видом надела или орошаемой/неорошаемой землей.

Садоводческий профиль также ограничен границами выбранного населенного пункта. Автоматический
поиск за его пределами по сельскохозяйственным или резервным землям не выполняется: отсутствие
кадастрового полигона не раскрывает категорию, собственника и разрешенное использование
пустого места. Для Кокшетау действует отдельная программная остановка садоводческого поиска,
пока официальное уведомление местного органа сообщает о приостановлении приема таких заявлений.

## Генпланы и ПДП

Реестр находится в панели `/admin/urban-plans`. Для каждого файла обязательны область,
район, населенный пункт, назначение (`все`, `ЛПХ` или `Садоводство`), тип слоя, наименование документа, акт утверждения, орган-источник,
официальная HTTPS-ссылка и EPSG. Поддерживаются три типа:

Слой назначения `ЛПХ` применяется как к прежнему профилю 10 соток, так и к режиму
`ЛПХ(новый поиск)`; отдельная загрузка одного и того же файла не требуется.

- `allowed` — территория, внутри которой квадрат выбранной площади должен помещаться целиком;
- `prohibited` — территория, любое пересечение с которой исключает кандидата;
- `red_line` — красная линия или полоса; применяется буфер `URBAN_PLAN_RED_LINE_BUFFER_M`.

Обычная загрузка GeoJSON через веб-панель создает отключенный черновик. Кнопка включения
недоступна, пока не подтверждены официальный источник, территория, SHA-256, актуальная
версия и независимая QA-проверка. Даже старый слой с `active=true` игнорируется поиском,
если у него нет `approved_for_search`, `verified_official`, `matched` и статуса
`STRICT`/`VERIFIED_STRICT`.

Производственный путь для PDF/JPG:

1. `tools.genplan_pipeline` создает неизменяемый manifest и хеширует исходники.
2. `tools.genplan_autoreg` выполняет только консервативную предварительную попытку.
3. `tools.genplan_workbench` сохраняет GCP оператора A1 со статусом `qa_pending`.
4. Другой оператор создает независимые checkpoint, а `tools.genplan_review` формирует
   `STRICT`, `WARNING` или `REJECT`.
5. `tools.genplan_export` разрешает рабочий GeoTIFF только для `STRICT`; `WARNING`
   экспортируется исключительно для теневой проверки.
6. После оцифровки доказанных зон `tools.genplan_import` проверяет всю цепочку хешей и
   транзакционно импортирует принятые GeoJSON в `UrbanPlanLayer`.
7. `tools.genplan_shadow` позволяет проверить слой на контрольных кандидатах до включения.

Для машиночитаемых слоев национальной АИС ГГК используется отдельный конвейер
`tools.genplan_ggk`. Он загружает функциональные зоны и красные линии через
официальный WFS, сохраняет исходные ответы, требует независимую проверку
действующего правового акта и формирует три слоя для `tools.genplan_import`.
Профили приусадебного ЛПХ, полевого ЛПХ и садоводства импортируются раздельно.
Подробные команды и формат проверки описаны в `tools/genplan_ggk/README.md`.
При импорте новой версии предыдущие активные слои того же документа и профиля
автоматически отключаются одной транзакцией.

GeoJSON должен быть получен из официального градостроительного документа с сохраненной
системой координат. Для полной градостроительной проверки населенного пункта нужен минимум
один принятый `allowed`-слой и доказанная полнота проверки исключающих зон и красных линий.
Слой без населенного пункта применяется ко всему указанному району. Оператор может отключить
устаревший слой, после чего он сразу перестает участвовать в новых поисках.

Публичная АИС ГГК и ЕГКН пока не дают одинаково полного машиночитаемого набора генпланов для
всех населенных пунктов. Поэтому система не угадывает назначение по цвету PDF и не считает
неофициальные изображения доказательством. В отчете сохраняются документ, зона и ссылка на
источник, использованные при проверке.

## Режимы поиска

- `SEARCH_MODE=live` — только актуальный публичный ЕГКН; основной режим сервера.
- `SEARCH_MODE=demo` — локальные демонстрационные данные для разработки.
- `SEARCH_MODE=hybrid` — живой поиск с резервными демо-данными; не рекомендуется для клиентов.

## Клиентская воронка

`CLIENT_FUNNEL_VERSION=v2` включает короткую клиентскую воронку RU/KZ:

- понятный выбор ЛПХ или садоводства без технических терминов на первом экране;
- выбор приусадебного или полевого ЛПХ и профиля 15/25 соток;
- одно редактируемое сообщение с фактическими этапами поиска;
- отдельные сообщения о завершении, бесплатных результатах и полном доступе;
- ApiPay/Kaspi без показа номера карты при включенной автоматической оплате;
- постоянный журнал событий в таблице `funnel_events`.

Для мгновенного возврата прежних текстов и кнопок используется
`CLIENT_FUNNEL_VERSION=v1`. Алгоритм поиска, бесплатный лимит, стоимость и права
оплаченного пользователя при переключении версии не меняются.

Поиск ЛПХ на 10 соток в V2 скрыт по умолчанию, но его код и обработчики
сохранены. Для временного возврата старой кнопки установите
`ENABLE_STANDARD_LPH_10=true`.

## Платежный процесс

### Бесплатный тестовый режим

Бесплатный лимит считается по участкам, а не по заявкам. При настройках
`FREE_PREVIEW_ENABLED=true`, `FREE_PREVIEW_PLOT_LIMIT=3` и
`PAID_SEARCH_ENABLED=true` каждый Telegram-пользователь может суммарно получить
до 3 расчетных участков:

1. Найденные участки сначала резервируются в пределах оставшегося лимита.
2. Бот сразу автоматически отправляет клиенту выбранное количество участков.
3. Заявки без результатов и технические ошибки лимит не расходуют.
4. Если доставка в Telegram прервалась, ее можно повторить из веб-панели.

Например, если первая заявка дала один участок, клиенту остается еще два. Если
следующая заявка дала десять вариантов, бесплатно будут отправлены только первые
два по рейтингу. После суммарной выдачи трех участков новые бесплатные результаты
не отправляются. Вместо этого бот предлагает единый бессрочный доступ ко всему
сервису за 4 990 ₸.
При `APIPAY_ENABLED=true` после нажатия клиент получает персональную кнопку
`Оплатить через Kaspi`. ApiPay присылает подписанное уведомление на
`POST /webhooks/apipay`, и после статуса `paid` доступ активируется автоматически
только для Telegram user ID этого клиента. Первый полный пакет отправляется
автоматически, а все дальнейшие поиски участков и функции земельных аукционов
работают без дополнительной оплаты.
Старый сценарий с номером карты, кнопкой `Я оплатил` и ручным подтверждением
администратором остается резервным при `APIPAY_ENABLED=false`.

1. Worker автоматически находит и геометрически проверяет варианты по ЕГКН.
2. После исчерпания тестового лимита клиент получает цену единого доступа 4 990 ₸ и кнопку активации без координат и кадастровых номеров.
3. После нажатия кнопки бот создает отдельный QR-счет ApiPay для заявки и показывает ссылку на оплату Kaspi.
4. Клиент оплачивает счет; возвращаться в бот и сообщать об оплате не требуется.
5. Обработчик проверяет HMAC-SHA256 подпись ApiPay, ID заявки, ID счета и точную сумму.
6. После статуса `paid` бот отправляет первый полный пакет и сохраняет единый доступ к поиску участков и аукционам за Telegram user ID клиента.
7. Каждый пакет содержит до 10 новых участков. После полной десятки появляется кнопка `Следующие 10 участков`.
8. Следующий поиск использует те же параметры и исключает все координаты, уже фактически отправленные этому пользователю в выбранном населенном пункте.
9. Другие Telegram-пользователи получают собственный бесплатный лимит и оплачивают активацию отдельно.

Рабочий адрес уведомлений должен быть публичным HTTPS-адресом на реальном домене,
сейчас production webhook: `https://zhertap.kz/webhooks/apipay`. Секреты хранятся только в
серверном `.env`:

```dotenv
APIPAY_ENABLED=true
APIPAY_API_KEY=
APIPAY_WEBHOOK_SECRET=
APIPAY_BASE_URL=https://api.apipay.kz/api/v1
APIPAY_TIMEOUT_SECONDS=30
```

Поиск возвращает до 10 вариантов и не требует найти ровно 10. Если не найдено ни одного
геометрического промежутка, клиент получает отдельное сообщение без запроса оплаты. Временные
ошибки ЕГКН и Telegram повторяются автоматически; после исчерпания попыток клиент получает
уведомление о технической ошибке и кнопку повторного поиска с теми же параметрами. Повторное
нажатие не создает дубликаты. Worker ограничивает одну попытку десятью минутами, поэтому заявка
не может бесконечно оставаться в обработке.

## Локальный запуск

```powershell
cd C:\Users\medadmin\Documents\Codex\2026-06-30\vj\land-scout-bot
```


## Перенос на Ubuntu

После переноса проекта и заполнения `.env`:

```bash
cd /opt/land-scout/land-scout-bot
sudo docker compose build --no-cache
sudo docker compose up -d --force-recreate
sudo docker compose ps
sudo docker compose logs --tail=100 web worker bot
```

После обновления старые заявки со статусом `failed` можно создать заново через Telegram.
Поля `TELEGRAM_BOT_TOKEN`, `ADMIN_PASSWORD`, `INTERNAL_API_KEY`, `POSTGRES_PASSWORD` и
`APP_BASE_URL` должны быть заполнены серверными значениями. PostgreSQL и Redis не нужно
публиковать наружу.
