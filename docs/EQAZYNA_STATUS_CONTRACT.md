# E-Qazyna: статусы торгов и правило отображения в Zhertap

## Два разных поля

E-Qazyna даёт два связанных, но не одинаковых вида статуса:

1. **Статус выдачи в списке** (`searchStatus`, технический код). Он выбирается в фильтре E-Qazyna и нужен для поиска карточек.
2. **Статус внутри карточки лота** (`Статус торгов:`). Он является детальным состоянием конкретной торговой процедуры и может меняться раньше/позже списка.

Zhertap хранит оба:

- `source_search_status` — код из списка E-Qazyna;
- `status` — текст из страницы конкретного лота.

В фильтре Zhertap используется первый, потому что это тот же набор, что в селекторе E-Qazyna. На карточке лота должен быть виден второй, детальный статус и дата последней проверки.

## Публичное соответствие фильтра

| Код E-Qazyna | Показывать в Zhertap | Значение |
|---|---|---|
| `ApplicationsAccept` | Прием заявок | Можно изучать условия и готовить действия на официальном портале. |
| `Pending` | Ожидание начала | Торги ещё не начались. |
| `Running` | Проводится | Торги идут. |
| `SuccessProtocolSigned` | Состоялся | Архивный результат, не текущий активный лот. |
| `FailureProtocolSigned` | Не состоялся | Архивный результат / возможный повторный аукцион. |
| `NullifyResultProtocolSigned` | Результат торга отменен | Нужна ручная сверка причины. |
| `CancelBeforeStart` | Отменен до начала торгов | Архивный результат. |

## Важное правило актуальности

- Значение списка не может автоматически перезаписывать подробный статус при ошибке/лимите источника.
- Страница `Ошибка исполнения` или `Превышен лимит запросов` не является карточкой лота и не сохраняется как лот.
- Если список и карточка расходятся, Zhertap должен показывать это как конфликт/устаревание и ставить повторную проверку, а не выбирать удобное значение.
- Отсутствие лота в неполном crawl не деактивирует сохранённый лот.

## Проверка перед заявлением о готовности

Для каждого статуса необходимы:

1. парсер тестовой карточки;
2. фильтр по техническому коду;
3. проверка отображаемой публичной подписи;
4. production read-back минимум одной реальной карточки, если источник её выдаёт;
5. отдельная фиксация ошибок источника и `Retry-After`.
