## Что сделано

- Автоматическая проверка использует только активные утвержденные GeoJSON-слои `VERIFIED_STRICT/search` из `urban_plan_layers`.
- Поддерживаются типы слоев `allowed`, `prohibited`, `red_line`.
- Проверка строгая: расчетный квадрат должен целиком попасть в разрешенную зону и не пересекать запретную зону или красные линии.
- ЛПХ 10 соток использует семейство `ЛПХ:household`; садоводство проверяется отдельными слоями `Садоводство`.
- Веб-кабинет и Telegram используют одну backend-логику проверки, поэтому статусы генплана должны совпадать.
- Добавлен genplan-first prefilter: если для выбранной территории есть подходящие утвержденные allowed-полигоны, поиск ЕГКН сначала сужается до пересечения района/населенного пункта с разрешенными зонами генплана.
- Если разрешенный слой есть в БД, но геометрически не покрывает выбранную заявку, система не должна блокировать весь район по одному широкому metadata-слою. Такой случай считается “нет пригодного цифрового слоя для этой точки/заявки”, после чего включается обычный сценарий предварительного результата без генплана.
- Если пригодного слоя нет, при `URBAN_PLAN_AUTO_WAIVE_UNAVAILABLE=true` заявка автоматически продолжает анализ без ручного подтверждения администратора. В отчете явно пишется, что генплан/ПДП не проверен автоматически.
- Ссылка для ручной сверки берется из `app/genplan_references.py` и локального индекса `app/data/manual_genplans.json`. Adilet должен быть только fallback, если нет карты/геопортала/PDF/JPG генплана.
- PDF/JPG генпланы можно показывать клиенту как материал для ручной сверки, но они не участвуют в автоматическом отсеве, пока не пройдены геопривязка A1/A2, QA и импорт в `urban_plan_layers`.
- Очереди разделены: поиск, платежи и recovery идут в `critical`; синхронизация аукционов идет в `auctions`, чтобы аукционный crawl не задерживал клиентские поиски.
- Если Overpass/OSM временно недоступен, поиск не должен падать: результат продолжается с пометкой, что дороги/объекты по OSM не были автоматически проверены.

## Что не сделано

- Нет честного 100% автоматического покрытия всех городов и поселков Казахстана по генпланам.
- 306 shadow/QA строк не влияют на клиентский поиск. Их нельзя включать без отдельного reviewed-релиза.
- PDF/JPG генпланы из локальной библиотеки еще не являются автоматической проверкой. Для каждого такого файла нужны контрольные точки, геопривязка, QA, векторизация/экспорт и импорт.
- Автоматическое чтение назначения зоны из произвольного PDF/JPG без геопривязки не включено, потому что это даст ложную уверенность и может неправильно отклонять или разрешать участки.
- Google/спутник не используется как юридический источник проверки. OSM используется только как открытый вспомогательный слой для дорог, объектов, воды и кладбищ.
- Финальная юридическая “свобода участка” не может гарантироваться системой. Пользователь все равно должен сверять результат с акиматом, земельным отделом, актуальным ПДП/генпланом и другими ограничениями.

## Практический смысл для клиента

Если генплан проверен автоматически, клиент видит, что найденное место прошло подключенный цифровой слой генплана/ПДП.

Если генплан не подключен, клиент все равно получает предварительный результат по ЕГКН/OSM, но в карточке должно быть простое предупреждение: “По этой территории у нас пока нет автоматической проверки генплана. Перед заявлением обязательно откройте карту/генплан и проверьте вручную.”

Если генплан показал ограничение, такие места не нужно продавать как подходящие. Их можно держать в админке для диагностики, но в клиентской выдаче они должны быть либо скрыты, либо показаны как неподходящие без CTA на оплату.
