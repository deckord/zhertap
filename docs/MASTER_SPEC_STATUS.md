# Общее ТЗ и статус реализации

Этот документ фиксирует большую картину проекта Land Scout Kazakhstan: что задумывалось, что уже реализовано, что сделано частично, что еще не сделано и почему. Его нужно читать в новом чате Codex вместе с `PROJECT_HANDOVER.md`, `ARCHITECTURE.md`, `OPERATIONS.md` и `INTEGRATIONS.md`.

По разделу `Аукционы v2` короткий понятный статус вынесен отдельно: [AUCTIONS_V2_STATUS.md](AUCTIONS_V2_STATUS.md).

По генпланам/ПДП последний production-аудит вынесен отдельно: [GENPLAN_STATUS_2026_08_17.md](GENPLAN_STATUS_2026_08_17.md). Ручная проверка всех 641 точек завершена (`queued = 0`); отдельно описаны активное боевое покрытие и backlog будущего расширения источников.

Статусы:

- `Выполнено` - функция уже есть в коде и работает в основном сценарии.
- `Частично` - основа реализована, но не закрывает весь изначальный замысел.
- `Не сделано` - в коде нет полноценной реализации.
- `Отложено` - сознательно не делали по решению владельца проекта.
- `Требует данных` - код/архитектура есть, но качество зависит от внешних официальных данных.

## 1. Общая цель проекта

Создать единую экосистему для работы с земельными данными Казахстана:

- поиск расчетных мест под ЛПХ и садоводство;
- мониторинг земельных аукционов;
- анализ инвестиционной привлекательности;
- поиск участков по пользовательским критериям;
- проверка ограничений;
- сравнение участков;
- оценка цены и рынка;
- помощь в подготовке формулировок для заявлений;
- накопление собственной исторической базы.

Статус: `Частично`.

Комментарий: Telegram-бот, backend, публичный сайт `zhertap.kz`, веб-кабинет, админка, оплата, поиск мест, аукционы, обратная связь и аналитика уже есть. Полная историческая база аукционов еще не завершена.

## 15. Что важно сделать следующим

Рекомендуемый порядок дальнейших работ:

1. `Высокий приоритет` - выполнить historical backfill E-Qazyna на production, проверить счетчики по статусам/периодам и понять фактическую глубину открытого архива.
2. `Высокий приоритет` - улучшить качество геоанализа аукционов: координаты, вода, дороги, ограничения, если будут надежные открытые слои.
3. `Средний приоритет` - расширить аукционную аналитику в админке: район/область/категория/динамика.
4. `Средний приоритет` - добавить карту активных аукционных лотов на отдельный frontend/админский экран.
5. `Средний приоритет` - расширять покрытие официальных генпланов/ПДП по новым городам только при появлении надежных геопривязанных данных; ручные 641 точки повторно размечать не нужно.
6. `Средний приоритет` - доработать web account-level оплату через сайт, если нужно принимать оплату без Telegram.
7. `Средний приоритет` - улучшать UX веб-кабинета по фактическим отзывам клиентов.
8. `Низкий приоритет` - PDF/Excel экспорт, если снова станет нужен.

## 16. Что не считать ошибкой

- Если в БД нет пригодного утвержденного слоя генплана/ПДП по выбранной территории, заявка автоматически продолжает анализ без этой проверки и явно пишет это в отчете.
- Если слой есть, но он сломан, спорный или кандидат попал в запрет/красную линию, автоматического обхода нет.
- Если найдено меньше 10 участков - это нормально; бот выдает до 10, а не ровно 10.
- Если E-Qazyna crawl incomplete и система не деактивирует старые лоты - это защита от ложного удаления.
- Если аукционный геоанализ не показывает расстояния - значит в данных лота нет координат/reference objects.
- Если расчетное место требует проверки акиматом - так и должно быть; бот не подтверждает юридическую свободу.
